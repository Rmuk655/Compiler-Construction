\section{Part 1: Exploring AST dumps}

\subsection{Program}
The input is \texttt{nested\_loops.cpp}: a function \texttt{f} containing a loop, and a \texttt{main} with a doubly nested loop (both loops use a variable called \texttt{i}) and a call to \texttt{f}.

\begin{Verbatim}[fontsize=\footnotesize,frame=single]
#include <stdio.h>

void f(int n){
    for(int i = 0; i < n; i++){
        printf("Hello World\n");
    }
}

int main(){
    int n = 10;
    for(int i = 0; i < n; i++){
        for(int i = 0; i < n; i++){
            printf("Hello World\n");
        }
    }
    f(n);
    return 0;
}
\end{Verbatim}

\subsection{Dumping the AST}
\begin{Verbatim}[fontsize=\footnotesize]
clang -fsyntax-only -Xclang -ast-dump -Xclang -ast-dump-filter=main nested_loops.cpp
\end{Verbatim}
\texttt{-ast-dump-filter=main} restricts the dump to the declaration named \texttt{main}; without it the headers pulled in by \texttt{<stdio.h>} dominate the output. The dump below has addresses and most source ranges removed for readability (the raw output is \texttt{ast\_dump\_main.txt}).

\subsection{Interesting nodes and their hierarchy}

\paragraph{1. \texttt{ForStmt}.}
A \texttt{for} loop is one node with four fixed child slots, in order: \emph{init} (\texttt{DeclStmt}), \emph{condition variable} (here \texttt{<<<NULL>>>}, used only for \texttt{for (...; T v = ...; )} forms), \emph{condition} (\texttt{BinaryOperator <}), \emph{increment} (\texttt{UnaryOperator ++}), and finally the \emph{body}. In the dump the body is a \texttt{CompoundStmt}, whose only child is the inner \texttt{ForStmt}. This is how loop nesting appears in the tree: the inner loop is a child of the outer loop's body, not a sibling.

\paragraph{2. \texttt{CallExpr}.}
\texttt{printf("Hello World\textbackslash n")} is a \texttt{CallExpr} whose first child is the callee expression and the remaining children are the arguments. The callee is not a bare \texttt{DeclRefExpr}: Clang wraps it in an \texttt{ImplicitCastExpr <FunctionToPointerDecay>}, so the node under \texttt{CallExpr} is the cast, and the \texttt{DeclRefExpr} naming \texttt{printf} is its child. The string argument is likewise wrapped in an \texttt{ArrayToPointerDecay} cast above the \texttt{StringLiteral}. A matcher for ``calls to \texttt{printf}'' therefore has to look through these implicit nodes, which \texttt{callee(functionDecl(hasName("printf")))} does for us.

\paragraph{3. \texttt{DeclStmt} / \texttt{VarDecl} / \texttt{DeclRefExpr}.}
\texttt{int i = 0;} is a \texttt{DeclStmt} (a statement) holding a \texttt{VarDecl} (the declaration), whose child is the initializer \texttt{IntegerLiteral}. Every later use of \texttt{i} is a \texttt{DeclRefExpr}, which does not copy the variable but \emph{refers} to a particular \texttt{VarDecl} (the dump shows \texttt{Var 0x...~'i'} before the addresses were stripped). The program declares \texttt{i} twice, so there are two distinct \texttt{VarDecl} nodes; each \texttt{DeclRefExpr} points to the nearest enclosing one, so the inner loop's \texttt{i} shadows the outer one. This declaration/reference link is exactly what is needed to decide whether a local variable is ever used (Part 2, pass 3).

\paragraph{Other nodes worth noting.}
\texttt{ImplicitCastExpr <LValueToRValue>} appears around every variable that is \emph{read} (\texttt{i} and \texttt{n} in \texttt{i < n}) but not around \texttt{i} in \texttt{i++}, where it is modified in place.
\texttt{CompoundStmt} is the \texttt{\{ ... \}} block and just holds a list of statements.
The overall root of this dump is \texttt{FunctionDecl}, which sits under the \texttt{TranslationUnitDecl}.

\section{Traversal mechanisms in Clang}

\paragraph{\texttt{RecursiveASTVisitor}.}
A CRTP base class. Derive from \texttt{RecursiveASTVisitor<Derived>} and define \texttt{VisitXxx(Xxx *node)} for the node kinds of interest; the base class walks the whole tree depth-first and calls them. Three layers exist per node kind: \texttt{TraverseXxx} (controls descent into children and can prune a subtree by not calling the base), \texttt{WalkUpFromXxx} (calls the \texttt{Visit} methods for the node and its base classes), and \texttt{VisitXxx} (what you usually override; return \texttt{false} to stop the whole traversal). Best for imperative analyses that need state across the walk.

\paragraph{AST matchers with \texttt{MatchFinder}.}
A declarative approach: describe the pattern as a composition of matchers (node matchers such as \texttt{forStmt}, \texttt{varDecl}; narrowing matchers such as \texttt{hasName}; traversal matchers such as \texttt{hasBody}, \texttt{hasCondition}, \texttt{hasDescendant}) and attach a \texttt{MatchCallback} to it with \texttt{MatchFinder::addMatcher}. \texttt{.bind("id")} labels sub-nodes, which the callback's \texttt{run} retrieves with \texttt{Result.Nodes.getNodeAs<T>("id")}. The finder does the walk internally. Concise for local patterns, and what Part 2 uses.

\paragraph{\texttt{ASTConsumer} and \texttt{ASTFrontendAction}.}
The hook by which a tool gets the AST at all. A \texttt{FrontendAction} creates an \texttt{ASTConsumer}, whose \texttt{HandleTranslationUnit(ASTContext\&)} (or \texttt{HandleTopLevelDecl}) is called once parsing finishes. From there one typically starts a \texttt{RecursiveASTVisitor} from \texttt{Context.getTranslationUnitDecl()}. \texttt{newFrontendActionFactory(\&Finder)} in a LibTooling \texttt{main} hides this for matchers.

\paragraph{\texttt{StmtVisitor} / \texttt{DeclVisitor}.}
Dispatch-only visitors: \texttt{Visit(node)} calls the \texttt{VisitXxx} for that node's dynamic type, but \emph{does not} recurse; you recurse manually via \texttt{node->children()}. Used inside Clang itself (e.g.\ the AST printer, code generation) when the traversal order is custom.

\paragraph{Direct child iteration and parent queries.}
Every \texttt{Stmt} exposes \texttt{children()}, and a \texttt{DeclContext} exposes \texttt{decls()}, for a hand-written walk. Clang nodes have no parent pointer; \texttt{ASTContext::getParents(node)} (backed by the \texttt{ParentMapContext}) computes the parent map on demand for upward navigation.

\section{Part 2: AST-matcher passes}

All three checks are in a single LibTooling tool built from \texttt{pass.cpp} (target \texttt{Simple\_Pass}), run as \texttt{Simple\_Pass file.cpp --}. Each check has a test input in \texttt{tests/}.

\subsection{Build and run}
\begin{Verbatim}[fontsize=\footnotesize]
cp -r 2-ast-matcher-passes ~/llvm-project/clang-tools-extra/Mypass
# add:  add_subdirectory(Mypass)  to clang-tools-extra/CMakeLists.txt
cd ~/llvm-project/build && cmake . && make -j4 Simple_Pass
bin/Simple_Pass ../clang-tools-extra/Mypass/tests/assign_in_condition.cpp --
\end{Verbatim}
Tested against LLVM/Clang 17.0.6.

\subsection{Pass 1: assignment inside a condition}
\textbf{Goal.} Flag \texttt{if (x = 5)}, where \texttt{==} was probably intended.\\
\textbf{Approach.} The five statement kinds that have a condition (\texttt{if}, \texttt{for}, \texttt{while}, \texttt{do-while} and the \texttt{?:} operator) each get a matcher of the form shown below (here for \texttt{if}), and the five are combined with \texttt{anyOf} under one \texttt{stmt(..., isExpansionInMainFile())}.
\begin{Verbatim}[fontsize=\footnotesize,frame=single]
ifStmt(hasCondition(ignoringParenImpCasts(
    binaryOperator(hasOperatorName("=")).bind("assignment"))))
\end{Verbatim}
\texttt{ignoringParenImpCasts} is needed because in C++ the condition \texttt{n = 13} is wrapped in an \texttt{ImplicitCastExpr} (int to bool), and \texttt{if ((n = 13))} adds a \texttt{ParenExpr}; both forms are therefore found. Only plain \texttt{=} is matched; compound assignments such as \texttt{+=} are not reported. The bind ID is placed on the \texttt{binaryOperator}, so the callback receives the assignment itself and prints its source location.\\
\textbf{Test.} \texttt{tests/assign\_in\_condition.cpp}\\
\textbf{Output.} Only the assignment on line 5 is reported; the comparison \texttt{n == 10} on line 8 is not.
\begin{Verbatim}[fontsize=\footnotesize,frame=single]
tests/assign_in_condition.cpp:5:8
\end{Verbatim}

\subsection{Pass 2: empty loop body}
\textbf{Goal.} Flag \texttt{for}, \texttt{while} and \texttt{do-while} loops whose body is an empty compound statement \texttt{\{\}}.\\
\textbf{Approach.} \texttt{forStmt}, \texttt{whileStmt} and \texttt{doStmt} each use \texttt{hasBody(compoundStmt(statementCountIs(0)))}, i.e.\ the body must be a block containing no statements, and all three bind the same ID \texttt{loop}. A loop whose body is a single statement or a bare \texttt{;} (\texttt{NullStmt}, as in \texttt{for (...);}) is deliberately not reported, since the question asks for empty compound statements. The matchers are restricted to the main file.\\
\textbf{Test.} \texttt{tests/empty\_loop\_body.cpp}\\
\textbf{Output.} Only the empty \texttt{for} on line 6 is reported; the \texttt{do} and \texttt{while} loops in the test have non-empty bodies.
\begin{Verbatim}[fontsize=\footnotesize,frame=single]
tests/empty_loop_body.cpp:6:5
\end{Verbatim}

\subsection{Pass 3: unused local variable}
\textbf{Goal.} Flag local variables that are declared but never referenced in their enclosing function.\\
\textbf{Approach.} Two matchers feed one callback: \texttt{varDecl(hasLocalStorage(), unless(parmVarDecl()))} records every local variable declaration, and \texttt{declRefExpr(to(varDecl(hasLocalStorage())))} records every use. Each variable has exactly one \texttt{VarDecl} node, and each use is a \texttt{DeclRefExpr} whose \texttt{getDecl()} points back to it, so the \texttt{VarDecl*} identifies the variable (two variables both called \texttt{i} are different pointers). The callback keeps a set of declared and a set of referenced pointers; after \texttt{Tool.run} the variables in the first set but not in the second are printed. The report cannot be produced inside the callback because a use may appear after the declaration. Parameters, globals and \texttt{static} locals are not reported. Any reference counts as a use, so a variable that is only written (\texttt{int c = 3; c = 4;}) is not reported.\\
\textbf{Test.} \texttt{tests/unused\_local.cpp}\\
\textbf{Output.} The unused \texttt{x} in \texttt{f} and the unused \texttt{x} in \texttt{main} are both reported; \texttt{n} and \texttt{i} are used and are not.
\begin{Verbatim}[fontsize=\footnotesize,frame=single]
Unused variable: x
Unused variable: x
\end{Verbatim}

\section{Limitations}
\begin{itemize}
\item Pass 1 reports only plain \texttt{=}; \texttt{if (x += 2)} is not reported. An assignment hidden in a function call or a lambda inside the condition is not found, because the matcher inspects only the condition expression itself.
\item Pass 2 does not report a \texttt{for (...);} or \texttt{while (...);} loop (a \texttt{NullStmt} body) or a body containing only an empty nested block.
\item Pass 3 counts any reference as a use, so write-only variables are missed; it does not report unused parameters, globals or \texttt{static} locals, and the report prints only the variable name (no source location).
\item All passes ignore code that comes from headers (\texttt{isExpansionInMainFile}), so problems inside included files are not reported. Macros and templates were not tested.
\end{itemize}
