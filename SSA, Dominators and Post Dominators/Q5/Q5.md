## Setup

I generated before.ll, after.ll for each of the 5 programs using the commands (given in README)
```bash
clang++ -std=c++17 -S -emit-llvm -O0 -Xclang -disable-O0-optnone "cpp Codes/N.cpp" -o IR/N_before.ll
opt -passes=mem2reg -S IR/N_before.ll -o IR/N_after.ll
opt -passes=verify -disable-output IR/N_after.ll
```
The flag -disable-O0-optnone is needed because clang normally adds the attribute optnone to functions compiled with -O0 but optnone attribute tells the llvm to skip most most optimization passes for that function including mem2reg.

## (a) What analysis information does mem2reg depend on?

The mem2reg pass uses information about the control flow graph and the definitions and uses of variables to convert eligible variables stored in memory into SSA form.

| Analysis | What it provides / how it is used |
| :-------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DominatorTreeAnalysis | Provides the dominator tree, which helps determine where PHI nodes are needed and how variables are renamed during SSA construction. |
| AssumptionAnalysis | Provides information about assumptions made in the program, such as `llvm.assume`. |
| TargetIRAnalysis | Provides target-specific information about the IR. |

- **Dominance frontier:** Helps identify where PHI nodes may be needed when a variable is assigned along different control-flow paths. LLVM can compute this information using the dominator tree.
- **Definitions and uses:** mem2reg identifies the stores and loads associated with each alloca and checks whether it can be safely promoted. Eligible allocas must generally be accessed through direct loads and stores.

Using this information, mem2reg inserts PHI nodes where required and renames variables so that each SSA value has a single definition.

## (b) What variables are converted to SSA form?

| Program | Function | Allocas before | Allocas after | PHIs before | PHIs after |
|---------|----------|----------------|---------------|-------------|------------|
| 1 | basicPointer | 3 | 0 | 0 | 0 |
| 2 | conditionalPointer | 4 | 2 | 0 | 1 |
| 3 | pointerEscape + modify | 4 | 1 | 0 | 0 |
| 4 | arrayPointer | 5 | 1 | 1 | 3 |
| 5 | heapPointer | 4 | 0 | 0 | 2 |

### Program 1: basicPointer

The variables `input`, `value` and `ptr` are promoted to SSA form. Their corresponding alloca, load and store instructions are eliminated.

Even though the address of `value` is initially stored in `ptr`, both variables can be promoted. Once `ptr` is promoted, its uses become direct uses of the address of `value`. This allows `value` to be promoted as well. The resulting IR uses SSA values directly instead of accessing these variables through memory.

### Program 2: conditionalPointer

The variables `condition` and `ptr` are promoted to SSA form. Their corresponding stack allocations and associated loads and stores are removed.

A pointer-valued PHI node is introduced at the join block. It selects between the address of `first` and the address of `second`, depending on which branch was executed. The selected pointer is then used to access and update the corresponding integer.

### Program 3: pointerEscape

In `pointerEscape()`, the variables `n` and `ptr` are promoted to SSA form. In `modify()`, the stack allocation used to store the parameter `p` is also eliminated because the parameter is already available as an SSA value.

The corresponding alloca, load and store instructions for these promoted variables are removed. However, the actual variable `value` remains memory-backed because its address is passed to `modify()`.

### Program 4: arrayPointer

The scalar variables `n`, `ptr`, `sum` and `i` are promoted to SSA form. Their corresponding stack allocations and associated loads and stores are removed.

PHI nodes are introduced for the loop-carried variables `sum` and `i`, since their values are updated during each loop iteration. The IR also contains a PHI node associated with the short-circuit evaluation of the `&&` condition.

### Program 5: heapPointer

The local stack variables `n`, `buffer`, `sum` and `i` are promoted to SSA form. Their corresponding stack allocations and associated loads and stores are eliminated.

Two PHI nodes are introduced at the loop header for `sum` and `i`, since their values are carried from one iteration to the next. The pointer variable `buffer` is also promoted, but the dynamically allocated array it points to remains in heap memory.

## (c) What variables are NOT converted to SSA form and why?

### Program 1

No variables remain unpromoted. All three local variables (`input`, `value` and `ptr`) are successfully converted to SSA form.

### Program 2

The variables `first` and `second` remain as allocas in memory. Their addresses are stored as incoming values to the pointer PHI node. Since the selected pointer is used to access and modify these variables indirectly, their memory accesses cannot be replaced with ordinary SSA values by mem2reg.

### Program 3

The variable `value` remains as an alloca in memory. Its address is passed to the function `modify()`, which accesses and modifies the value through the pointer. Therefore, mem2reg cannot promote this variable in this example.

### Program 4

The array `arr` remains memory-backed. Its elements are accessed using computed addresses through GEP instructions. Since the array is accessed as an aggregate through indexed memory operations rather than as a single scalar variable, it is not promoted by mem2reg in this example.

### Program 5

The dynamically allocated array created using `new int[n]` remains in heap memory. mem2reg operates on eligible stack allocations created using `alloca`, not dynamically allocated heap objects.

The local pointer variable `buffer`, which stores the address of this heap allocation, is promoted to SSA form. However, the actual heap array and its load/store operations remain unchanged.

## Conclusion

The mem2reg pass converts eligible stack-allocated variables into SSA values by eliminating unnecessary alloca, load and store instructions. It uses dominator information and inserts PHI nodes wherever values from different control-flow paths need to be merged. 
However, variables accessed indirectly through pointers, arrays accessed through computed addresses, and dynamically allocated heap objects may remain memory-backed when they do not satisfy the promotion requirements.
